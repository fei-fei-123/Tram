# 插件设计

插件是Tram的执行单元，一次Tram执行将会在不同生命周期中，执行不同的插件方法。插件通过插件方法来进行初始化。然后通过注册过滤器等方式实现对会话上下文处理。

这篇文档会从宏观的角度介绍，如何开发一个好的插件，而不去介绍具体开发方式。希望开发者读完这篇文档后，能够理解插件的设计理念，从而写出来一个优秀的插件。

文中伪代码均为语义示意：形如 `self.xxx(ctx, ...)` 的调用，表示向通信层提交了对应的操作（见[[上下文设计#操作 Operation|操作]]），这些方法由插件自行实现，程序并不提供。

# 设计原则

由于程序不关注插件的运行过程，但是对插件的运行结果有着极高的要求（因为涉及到了任务能够顺利完成）。因此，程序希望插件的设计能够遵循以下原则。

## 工作前提不确定

插件不能依赖一个前提才能工作。因为程序并不能够保证提供这样的一个前提。即使是在一个Tram中顺利运行了，也无法提供保证能在另一个Tram中顺利运行。因为插件就是这样的一个东西。

一个好的设计，是不依赖任何前提就能实现某种功能的。即使无法避免的需要这样的条件，插件也需要自己处理“如果没有这样的条件，那么要怎么做”的问题。具体怎么做，则交给插件自己决定。

一个坏的设计如下：

```python
# 这是一个读文件的插件的部分功能
def func(self, ctx):
	if self.need_read_file(ctx):
		file_path = self.get_file_path(ctx)
		# 错误：既然上下文中已经有了，那么我就无条件信任这个文件一定存在
		self.read_file(file_path)
```

这里是错误的设计依据。程序并不能够保证“文件一定存在”的这样一个前提。插件不应该将“这个文件，其他插件或者程序已经确认过”作为前提运行。其他插件和程序没有这个义务来帮助你运行，你也不需要帮助其他插件顺利进行。

一个好的设计如下：

```python
# 这是一个读文件的插件的部分功能
def func(self, ctx):
	if self.need_read_file(ctx):
		file_path = self.get_file_path(ctx)
		# 正确：这个文件没有被校验过，我需要确认这个文件是否存在
		if self.check_file(file_path):
			self.read_file(file_path)
		else:
			# 正确：失败时不止提交错误，还要把句柄替换成失败说明
			# 否则下一轮LLM看到的仍是未处理的句柄，同样的失败只会重复发生
			self.set_curr_msg(ctx, "读取失败：文件" + file_path + "不存在")
			self.submit_error(ctx, "文件不存在：" + file_path)
			self.new_turn(ctx)
```

在这里，插件没有将“这个文件已经被确认过”作为前提运行，相对应的，插件自己确认了这个文件是否存在。并且，还为文件不存在的情况做了对应的处理：提交错误记录、把句柄替换成失败说明、再申请续轮。如果只提交错误而不处理句柄，下一轮LLM看到的仍是一个未处理的句柄，同样的失败只会重复发生，直到烧光轮次上限。这意味着，这个插件已经能够相对“漂亮”的完成了程序交给它的工作。

## 上下文不原始

插件拥有着对于上下文的极强的权限与能力。每个插件都应该明确一个事实：“我拿到的上下文并不是原始的上下文”。即使确实没有其他插件更改了上下文，但依然应当认为，接下来插件拿到的上下文已经被修改过了。

实际上这个情况与工作前提不确定的意义很像，但是其实是一件事情的两个方面。一个是协作方面，一个是工作方面。

一个好的设计，不会将上下文当成仅有我参与工作的服务。应当需要考虑到，其他的插件添加、修改、删除了某些信息。从而设计相应的逻辑与工作。

一个坏的设计如下：

```python
# 这是修改提示词插件的部分功能
def func(self, ctx):
	msg_list = self.get_msg_list(ctx)
	# 错误：我认为第一条消息就是系统提示词
	sys_msg = msg_list[0]
	# 错误：我将系统提示词改成我需要的提示词
	sys_msg.content = "提示词"
```

这个插件有三个问题。

首先就是插件错误的认为第一条消息就是系统提示词。虽然通常来说是这样的。但是如果有些插件更改了系统提示词的位置，那么将无法顺利的修改到正确的信息。

其次，这个插件使用直接赋值来修改系统提示词。这违反了“一切操作必须经过通信层”的约定：插件从读取操作中拿到的是深拷贝克隆，直接修改克隆，根本不会作用到真正的上下文上。

最后，即使插件改为通过通信层提交写操作，也仍有隐患：写操作是整条替换。如果不先读取原有内容、在原有基础上追加，那么其他插件对系统提示词的修改将不复存在。这是非常糟糕的Bug，会导致其他插件无法按期望顺利进行。

一个好的设计如下：

```python
# 这是修改提示词插件的部分功能
def func(self, ctx):
	msg_list = self.get_msg_list(ctx)
	idx = 0
	# 正确：不假设位置，逐条检查，找到第一条系统提示词
	while idx < len(msg_list) and not self.is_sys_msg(msg_list[idx]):
		idx+=1
	
	if idx < len(msg_list):
		sys_msg = msg_list[idx]
		# 正确：在原有内容的基础上追加，再经通信层的写操作写回
		# 直接修改克隆不会生效，一切操作必须经过通信层
		self.write_msg(ctx, sys_msg.id, sys_msg.content + "提示词")
	else:
		self.add_system(ctx, "提示词")
```

这个插件就是在其他插件已经修改过上下文的前提下工作的。它不假设系统提示词的位置，而是逐条检查、找到第一条系统提示词。拿到提示词之后，也并没有直接覆盖，而是在原有内容的基础上追加，并经通信层的写操作写回。除此之外，也处理了会话中不存在系统提示词的情况。

## 多个插件好于一个插件

当设计插件时，别忘了审视对于自己插件的各种定位。通常来说，一个插件应当尽可能聚焦于一个（或者一系列）功能。如果你发现你的插件对于各种功能都有涉及，那么我认为你应当重新考虑这个插件是否应当拆成多个插件。

为什么要拆成多个插件？因为插件对于用户是可选的。Tram设计之初就是为了方便开发者和用户配置插件。那么不可避免的就会导致，用户可能只想要A插件的其中一个功能，且不喜欢另一部分功能。同时B插件的这一部分功能做的更好。如果同时安装两个插件，则会导致功能重复。

但是必须要强调，我并没有要求插件必须只能拥有一个功能。插件的功能应当聚焦于同一个系列，如记忆的回归与保存、技能的查找与调用等。

一个坏设计如下：

```python
# 这是一个全能插件
def func(self, ctx):
	self.search_network()
	self.search_memory()
	self.check_skill()
	self.llm.chat()
```

这个插件做了四个领域的事情：

1. 网络搜索资料
2. 搜索记忆
3. 检查技能
4. 调用LLM

这并不是一个好的设计，因为当安装了这个插件之后，再次安装其他功能更好的插件的时候，则不可避免的功能重复，从而造成种种浪费。

一个好的插件应当只聚焦于一个领域的功能：

```python
# 这是一个网络插件
def func(self, ctx):
	self.search_network()
	
# 这是一个记忆插件
def func(self, ctx):
	self.search_memory()
	
# 这是一个技能插件
def func(self, ctx):
	self.check_skill()
	
# 这是一个大模型插件
def func(self, ctx):
	self.llm.chat()
```

将4个功能拆成4个插件，将大大的提高用户的选择与体验。这要求开发者对于各个插件的可兼容性提出较高的标准。也就是即使拆成了4个插件，也要能实现原来1个插件的功能。

## 避免不必要的操作

通常来说，如果没有任何的必要，则不要进行任何对于上下文的操作。这个很好理解，因为用户明确的知道你对上下文做了什么，但是却完全不知道你实际做了什么工作。他们会在日志中看到，你读取了上下文。但即使你读取了，却什么也没看，也会对用户造成不必要的困扰。

坏的设计如下：

```python
# 这是一个发送一条时间戳插件的部分功能
def func(self, ctx):
	# 错误：读取了上下文信息却没有任何的消费，Just I like
	self.read_msg(ctx)
	self.send_msg(ctx)
```

这个插件就犯了这个错误。进行了一次没有必要的读操作。此时用户会注意到，一个完全没有必要读上下文的插件，读取了我的信息。很有可能会对这个插件困惑，担心自己的信息被窃取。

好的设计如下：

```python
# 这是一个发送一条时间戳插件的部分功能
def func(self, ctx):
	# 正确：仅做了必要的操作
	self.send_msg(ctx)
```

不必多说。插件仅做了必要且合理的工作。此时用户就不会困惑。
