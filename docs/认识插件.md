# 认识插件

在开始开发插件之前，我们应当认识插件。插件在Tram中，是执行单元。换句话说，任何拥有（没有也行）执行能力的东西都可以在Tram中注册为插件，插件可以是：

1. 一系列HTTP请求
2. 对文件、数据库的操作
3. 更改上下文的能力
4. 管理系统
5. 什么也不做
6. 一整个MCP ~~（如果真的有必要的话）~~
7. 另一个Tram ~~（额，如果想这么做的话）~~
8. 用户  ~~（额，毕竟用户的行为与插件的行为也可以是一样的）~~
9. 蜜雪冰城

综上所述，插件可以并不只是一个功能，做一些工作的工具。很大的功能来源完全取决于开发者的想象力。

这篇文档将会从宏观的角度，试图说明白什么是插件

# 定位与职责

首先我们应当抛弃传统Agent中的插件的关系。**传统插件与Tram插件相同点仅仅是共用了“插件”这个名字**。以下内容，如果还在试图寻找插件之间的异同，可能会导致理解十分困难。

## 插件与Tram

插件就是Tram的行为本身。插件与Tram是可以看成是独立的两个程序。但Tram和插件的关系又远远不是主人与仆从的关系。

### Tram离不开插件

Tram没有插件则没有行为，而没有行为则无法实现任何功能。Tram将作为Agent的一切行为都交给了插件，由插件来决定Tram应该怎么执行。

这意味着，在Tram中，插件才是主导者。通过插件的行为，组装成一个复杂的链路。

### 插件可以离开Tram

可是反过来，插件并不依附于Tram而存在。插件本体是一个自包含的模块：通过Manifest报备入口与工厂方法，由程序装载成实例并管理。至于插件内部做什么——纯函数、一系列HTTP请求、甚至包裹一个独立运行的子进程——都是插件自己的事。开发者以插件的方式，将自己的程序暴露出一个入口，供Tram自动（或半自动）的调用。

这意味着，在插件中，Tram只是负责人。

## 插件与插件

插件与插件的关系更为复杂，有着强相关的上下级关系，又在逻辑上平权。插件与插件是Tram的共同协作者

插件与插件的协同配合不是可选项，是必然要求。插件的设计之初就是默认存在着其他的插件。既要实现自己的功能，又不能干扰其他插件的正常运行就是插件的行为美学。

### 上下级

插件可以依赖于其他插件的结果（不过这种依赖关系可能不被满足）。通过链式调用，插件可以在合适的位置，合适的时机，合适的方式，与其他插件协同配合，从而请求其他插件帮助你、配合你、调用你。

### 平级

插件也可以完全无视其他插件，做自己的事。不需要参与插件的配合与帮助，甚至可以打断、阻止插件之前的协同配合。


# Tram与DSH的区别

实际上很难从现象上说明白同样都是插件就是一切，同样多一个插件就多一个功能的两个程序有什么区别。我不得不单开一个章节来说明，两个Agent之间的区别。

## DSH

包括DSH在内的其他可以安装插件的Agent在内。插件对于它们来说，是一种可选项。有了插件，产品会更好用。没了插件，产品依然还是产品。因此，插件是依赖于整个回复的生命周期的。

* 用户发来一个请求
* **程序**：好的，有哪个插件要来参与吗
* *插件A*：我来
* *插件B*：我来
* *插件C*：我来
* **程序**：好的，还需要再来一轮，还有别的插件要来吗
* 。。。

可以看到，整个回复流程，以程序为主，插件为辅。插件是整个回复中的可选操作。没有了插件不会对程序与任务产生影响。

## Tram

Tram将作为Agent的能力下发到了各个插件。插件对于Tram作为一种必然。因此，插件在设计上是自由的、控制是反转的、程序是独立的。

* 用户发来一个请求
* **程序**：好的，不管怎么样，我需要一个答案
* *插件A*：我先来
* *插件B*：我不参与
* *插件C*：或许应该再来一轮
* **程序**：好的，还需要再来一轮，你们给我一个答案吧
* 。。。
